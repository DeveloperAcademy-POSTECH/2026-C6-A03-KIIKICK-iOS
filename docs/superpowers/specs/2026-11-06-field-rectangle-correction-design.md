# 운동장 좌표 보정 — 직사각형化 Design

> `2026-10-27-field-heatmap-design.md`의 "1. 운동장 등록", "2. 좌표 변환 — FieldCoordinateMapper" 섹션을 대체한다. 나머지 섹션(운동장 연결, 히트맵 렌더링)은 그대로 유효.

## Overview

기존 설계는 사용자가 찍은 4점을 순서 무관한 사각형으로 보고, 위경도 → 정규화 좌표를 **매 GPS 샘플마다** bilinear 보간의 역변환(Newton-Raphson)으로 계산했다. 이 문서는 그 방식을 대체한다: 운동장 **등록 시점에 1회**, 4점을 "진짜 직사각형"으로 보정해서 저장하고, 히트맵 계산 시점에는 단순 회전+스케일 변환만 쓰게 한다.

## 배경 / 동기

- 매 샘플 사변형 역보간 대신, 등록 시점 1회의 보정 계산으로 비용을 옮긴다 — 히트맵 렌더링·스크러빙이 훨씬 가벼워진다.
- 직사각형 격자여야 히트맵 셀 분할/보간 로직이 단순해지고, 사변형 투영에서 오는 왜곡이 없다.

## 1. 핀 UI 변경

- 기존 드래그 가능한 사각형 프레임(`ResizableRectangleView`, 이슈 #2 1차 구현)을 제거한다.
- MapKit에 고정되는 커스텀 핀 4개를 사용자가 순서 상관없이 탭해서 찍는 방식으로 바꾼다.
- 탭 순서는 신뢰하지 않는다 — 사용자가 둘레를 따라 순서대로 찍는다는 보장이 없어서,
  순서에 의미를 두면(터치라인/골라인 방향 encode 등) 사용자가 실수로 다르게 찍었을 때
  보정이 크게 틀어질 위험이 있다. 대신 FieldRectangleCorrector가 4점의 중앙값(centroid)
  기준 각도로 정렬해 직접 올바른 둘레 순서를 만든다 — 아래 §2 참고.

### 1-1. 구현 방식 — 지도 전체를 덮는 투명 오버레이 대신 Map 자체의 네이티브 컴포넌트를 쓴다

1차 구현은 `Color.clear` + `DragGesture`로 Map 전체를 덮는 투명 레이어를 깔고 그 위에서
탭 위치를 좌표로 변환하는 방식이었다. 문제 2가지가 드러났다:
- 이 오버레이가 `.gesture()`(배타적)로 터치를 통째로 가로채서, Map 자체의 핀치줌/팬
  같은 기본 제스처가 전혀 먹지 않았다.
- 핀을 찍을 때 사용자가 의도한 위치와 다른 곳에 찍히는 문제도 있었다(세이프 에리어
  오프셋으로 좌표 변환이 어긋나는 등, 오버레이가 Map과 별도 좌표계를 다루면서 생기는
  부류의 버그).

그래서 투명 오버레이 자체를 없애고, Map의 기존 컴포넌트를 그대로 활용하는 방향으로
바꿨다:
- **핀 추가**: `SpatialTapGesture`를 Map 자체에 직접 붙인다(별도 오버레이 뷰가 아니라
  Map 뷰 그 자체에). main의 가장 처음 스캐폴드가 이미 이 패턴이었다 — 오버레이 방식은
  그 이후에 들어온 것.
- **핀 표시/드래그**: `Map { }` 콘텐츠 빌더 안에 `Annotation(coordinate:)`으로 핀을
  올린다. SwiftUI MapKit에는 UIKit의 `MKAnnotationView.isDraggable` 같은 내장 드래그
  API가 없어서, `Annotation`의 커스텀 콘텐츠 뷰 자체에 `DragGesture`를 붙인다 — 이 뷰는
  핀 하나 크기로 작아서, 지도 전체를 덮던 예전 오버레이보다 네이티브 팬/핀치와 덜
  충돌한다.
- **핀을 잇는 점선**: `MapPolyline(coordinates:)`를 `Map { }` 콘텐츠 빌더 안에 넣고
  `.stroke(색, style: StrokeStyle(dash:))`로 그린다 — 지도 좌표계에서 직접 그려지니
  수동 좌표 변환(`proxy.convert`) 없이 팬/줌에 자동으로 따라온다.
- **돋보기(loupe) 미세조정 UI는 없앤다** — 오버레이 전용 커스텀 기능이라 네이티브
  Annotation 드래그 방향과 안 맞는다.
- **운동장 검색(MKLocalSearch) 뷰도 없앤다** — 개발 리소스 대비 우선순위가 낮다고 판단.
- 내 위치로 돌아오는 버튼, 뒤로가기 버튼, "추가" CTA 버튼은 그대로 유지한다.

## 2. 사각형 보정 로직

사용자가 찍은 4점(위경도 → 로컬 평면/미터 좌표 변환 후, 변환 로직은 범위 밖)에서
기준각(axis) 하나를 계산한다. 먼저 탭 순서와 무관하게 올바른 둘레 순서를 직접 만들고,
그 다음 기준각을 구한다.

### 2-1. 둘레 순서 재정렬 — 중앙값 기준 각도 정렬

4점의 중앙값(centroid)을 구하고, 각 점을 "중앙값에서 그 점을 향하는 각도"로 정렬한다
(북쪽이 위인 지도를 기준으로 시계방향). 볼록한 사각형이면 이 정렬이 항상 올바른 둘레
순서(인접한 점끼리 이어지는 순서)를 만들어낸다 — 사용자가 어떤 순서로, 심지어 대각선부터
찍어도 결과가 같다. 이후의 모든 계산(§2-2의 변 길이/각도 포함)은 이 재정렬된 순서를 쓴다.

### 2-2. 기준각 계산 방법 후보 4가지

인터랙티브 비교 자료: **[기준축 선택](https://claude.ai/code/artifact/d5781d5e-e95e-4667-8369-1fac1b17d79f)** — 4점을 직접 드래그하면서 아래 네 방식의 결과를 비교할 수 있다. (이 자료는 중앙값 재정렬 이전에 만들어져 탭 순서를 그대로 썼지만, 축 선택 방식 자체를 비교하는 데는 유효하다.)

| 방식 | 규칙 | 장점 | 단점 |
|---|---|---|---|
| 대변 평균 | 마주보는 두 변(e1·-e3, e2·-e4)의 각도를 각각 평균 | 4점을 전부 반영, 노이즈에 가장 안정적 | 계산이 제일 복잡함 |
| **최장변 기준 (권장)** | §2-1로 재정렬된 순서로 이어지는 4개 변(0→1, 1→2, 2→3, 3→0) 중 가장 긴 변의 각도를 그대로 사용 | 계산 단순, GPS/탭 오차에 상대적으로 안정적(아래 참고) | 가장 긴 변 하나의 오차에 좌우됨 |
| 탭 순서 기준 | 1→2번 핀을 잇는 첫 변의 각도를 그대로 사용 | 계산이 제일 단순 | §2-1 재정렬 도입 전엔 1·2번 핀이 짧은 변·대각선에 가까우면 기준각이 크게 틀어지는 문제가 있었음(지금은 재정렬 때문에 애초에 "1·2번 핀"이라는 개념 자체가 없음) |
| 최소자승 피팅 | 4변의 각도를 mod 90°로 순환평균 | 통계적으로 가장 "정답"에 가까움 | 구현·검증 비용이 가장 큼, 과한 정밀도 |

**권장: 최장변 기준.** ±0.8m GPS/탭 오차로 2000회 시뮬레이션한 결과, 최장변 기준이 탭
순서 기준보다 각도 오차가 평균 절반 수준(1.52도→0.76도, 최대 4.5도→2.2도)으로 작았다.
축구/풋살 운동장은 터치라인이 골라인보다 뚜렷이 길기 때문에, 재정렬된 4개 변 중 가장
긴 변이 거의 항상 실제 터치라인과 일치한다.

### 바운딩 박스 — 항상 바깥으로만 확장

기준각이 정해지면, 그 각도로 4점을 회전시킨 좌표계에서 min/max로 바운딩 박스를 구해 직사각형을 만든다. 이 방식은 구조적으로 4점을 전부 포함하도록 **항상 바깥으로만 확장**되고 안쪽으로 깎이지 않는다 — 사용자가 찍은 실제 플레이 영역이 보정 과정에서 잘려 히트맵 데이터가 누락되는 걸 방지한다. 네 방식 중 어느 걸 쓰든 이 성질은 동일하다(축 선택 기준이 달라도 결과가 "조금 더 넓어지거나 좁아지는" 정도이지, 핀이 사각형 밖으로 밀려나는 일은 없다).

## 3. 저장 데이터

- 사용자가 찍은 원본 4점(raw)과 보정된 직사각형 4점(corrected)을 **모두** 저장한다 — 재보정·디버깅 대비.
- 서버에도 원본+보정 좌표를 함께 보내는 방향으로 백엔드와 협의 예정 (API 계약 변경 필요, 미확정).

## 범위 밖 (Out of scope)

- 극단적으로 찌그러진 입력(이상치) 처리/경고: [이슈 #39](https://github.com/DeveloperAcademy-POSTECH/2026-C6-A03-KIIKICK-iOS/issues/39)로 분리, 지금은 구현하지 않는다.
